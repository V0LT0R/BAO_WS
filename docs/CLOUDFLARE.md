# Перенос BAO в собственный аккаунт Cloudflare

Этот вариант размещает сайт в аккаунте владельца: React-страницы и API работают в Cloudflare Workers, записи и учётные записи — в D1, изображения сертификатов и проектов — в Workers KV. SQLite Durable Objects обслуживают авторизацию и изменения контента. Дизайн, адреса `.html`, языки и возможности админки сохранены. Публикация через сторонний сервис Sites не используется.

На **9 ноября 2026 года** сайт опубликован на `https://bao-cv.com` в собственном аккаунте Cloudflare. DNS-зона активна, оба Custom Domain подключены к своим Workers. На основном домене завершена проверка API и админки: `/api/health` возвращает `platform: cloudflare`; проверены вход с защищённой cookie и CSRF, создание, чтение, редактирование и удаление сертификата и проекта с PNG-изображениями, а также выход. Временные записи и изображения удалены; очистка проверена. HTTP перенаправляется на HTTPS кодом 301, а HTTPS `www` — на основной домен кодом 308; путь и параметры запросов сохраняются.

| Конфигурация | Worker | Назначение |
| --- | --- | --- |
| `wrangler.jsonc` | `bao-ws` | Сайт, API и админка на `bao-cv.com`; `PUBLIC_ORIGIN=https://bao-cv.com` |
| `wrangler.redirect.jsonc` | `bao-cv-redirect` | Только перенаправление `www.bao-cv.com` → `https://bao-cv.com` кодом 308 с сохранением пути и query string |

В обеих конфигурациях отключены `workers_dev` и `preview_urls`. Прежний технический адрес `bao-ws.bya20102005.workers.dev` не является адресом для проверки после этого переключения. Основной Worker продолжает отдавать статические файлы до запуска кода API; отдельный Worker для `www` не содержит привязок к базе или медиа.

После переноса и удаления проверочных данных в D1 сохранены исходные **1 аккаунт и 37 записей контента**. Привязки аккаунта, D1 и KV закреплены в `wrangler.jsonc`: обновление кода не требует повторного импорта или создания хранилищ. Проверенные версии деплоя: основной Worker — `65039065-b96a-4338-914d-d74bf8b44aca`, Worker перенаправления — `38b71129-aaf6-431b-ae1e-f4459bcdd4ca`.

## 1. Аккаунт и ограничения бесплатного варианта

Создайте свой аккаунт на [Cloudflare](https://dash.cloudflare.com/sign-up), подтвердите почту и включите двухфакторную аутентификацию. Используйте Workers Free и бесплатный план DNS-зоны. Для этого проекта не нужны R2, платный Workers или подключение платной подписки: не включайте их при настройке.

Это бессерверное приложение: отдельная виртуальная машина не запускается и не «засыпает». Процесс может заново инициализироваться при запросе; это не обещание нулевой задержки при любом обращении. Прогревать сайт регулярными запросами не требуется.

Основные квоты по документации на 8 ноября 2026 года:

| Ресурс | Бесплатная квота | Для чего используется |
| --- | --- | --- |
| Workers | 100 000 вызовов в день; 10 мс CPU на обычный вызов | API и маршрутизация |
| Static Assets | Запросы к статическим файлам бесплатны | React, CSS, шрифты, исходные изображения |
| D1 | 5 ГБ; 5 млн прочитанных и 100 000 записанных строк в день | Контент, пользователи, сессии |
| KV | 1 ГБ; 100 000 чтений и по 1 000 записей/удалений/списков в день | Загруженные изображения |
| SQLite Durable Objects | Доступны на Free; по умолчанию до 30 секунд CPU на вызов | bcrypt и последовательная обработка изменений |

Обычный Worker не выполняет bcrypt с коэффициентом 12: эта работа вынесена в `AuthService`. Квоты считаются на аккаунт; большой импорт тоже расходует лимиты KV. Перед переносом большого архива проверьте его объём и число файлов. Источники: [Workers](https://developers.cloudflare.com/workers/platform/limits/), [Static Assets](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/), [D1](https://developers.cloudflare.com/d1/platform/pricing/), [KV](https://developers.cloudflare.com/kv/platform/pricing/), [Durable Objects](https://developers.cloudflare.com/durable-objects/platform/limits/).

## 2. Подготовка и проверка на компьютере

Откройте терминал в корне проекта. Нужен Node.js 24.x, начиная с 24.15, и зависимости из lock-файла:

```powershell
npm ci
npm run build:cloudflare
npm run db:cloudflare:local
npm run test:client
npm run test:cloudflare
```

Сборка создаёт `dist`: десять React-страниц, собранные JS/CSS, разрешённые исходные изображения, шрифты, стили, поисковые файлы и `_headers`. Серверные исходники, `.env`, старые браузерные скрипты и карты исходников в статическую публикацию не попадают.

Для локального запуска:

```powershell
npm run dev:cloudflare
```

Откройте **http://localhost:8787**. Используйте именно этот адрес: он соответствует локальному `PUBLIC_ORIGIN`, который проверяется при входе и изменении данных. Локальные D1/KV хранятся в игнорируемой папке `.wrangler`; это отдельные данные, не облачная база.

Команды `npm run cf -- ...` запускают установленный в проекте Wrangler. Обёртка сохраняет локальные служебные файлы в игнорируемых каталогах и не загружает MongoDB-настройки из `.env` в Worker. MongoDB и Express для работы Cloudflare-варианта не нужны.

## 3. Перенос существующих записей и изображений

Сохраните резервную копию действующей MongoDB вместе с GridFS. На время окончательного экспорта остановите редактирование контента в старой админке, чтобы новые записи не остались только на старом сайте.

В экспорте указывается **точное имя исходной базы**, а не строка подключения. Вместо `NAME` подставьте имя из своей конфигурации. Если старая MongoDB URI не содержит имени базы, драйвер использует `test`; инструмент сверяет подтверждение с фактическим именем. Конфигурация читается из существующего локального `.env`:

```powershell
node scripts/migrate-cloudflare.mjs export --confirm-database NAME
```

Экспорт читает MongoDB и GridFS, не изменяя их; переносимые изображения локально проверяются и перекодируются в WebP. Скопируйте точный путь к созданному `manifest.json` из вывода команды. Архив в `.migration` содержит данные пользователей и хеши паролей: он исключён из Git, но его всё равно следует хранить как резервную копию с ограниченным доступом. Не отправляйте его в чат и не загружайте в репозиторий.

Сначала проверьте импорт локально; замените путь в примере своим:

```powershell
node scripts/migrate-cloudflare.mjs import --manifest ".migration/export-.../manifest.json" --local
```

Импорт рассчитан на **пустую целевую базу**, а для архива с изображениями — также на пустой namespace `MEDIA`. Если он сообщает о существующих данных или частично перенесённых файлах, не очищайте рабочее хранилище ради повторного запуска: сначала выясните, какой импорт уже выполнен. При переносе сохраняются существующие учётные записи и совместимые bcrypt-хеши; администратор входит своим паролем. Старые активные сессии не переносятся.

После импорта проверьте вход, списки проектов/опыта/активностей, изображения и оба языка. На локальной копии добавьте, отредактируйте и удалите пробный сертификат.

## 4. Публикация в настроенный аккаунт

Авторизуйте локальный Wrangler в своём аккаунте:

```powershell
npm run cf -- login
npm run cf -- whoami
npm run build:cloudflare
npm run deploy:cloudflare:all
```

В рабочем `wrangler.jsonc` уже сохранены выданные владельцу ID аккаунта, D1 `DB` и KV `MEDIA`. `wrangler.redirect.jsonc` указывает на тот же аккаунт. Проверьте результат `whoami` перед публикацией; не заменяйте рабочие ID и не создавайте заново хранилища для обычного обновления кода.

`npm run deploy:cloudflare` публикует только основной Worker из `wrangler.jsonc`; эта команда сохраняется для существующей автоматической сборки сайта. Для ручной публикации обоих используйте `npm run deploy:cloudflare:all`: сначала обновляется основной Worker, затем перенаправление из `wrangler.redirect.jsonc`. Если первый деплой завершился ошибкой, второй не запускается. Это не атомарная операция: при ошибке второго первый уже может быть обновлён. Проверьте оба результата в терминале. Для публикации только перенаправления:

```powershell
npm run deploy:cloudflare:redirect
```

До первого подключения доменов выполните шаги раздела 6: существующие записи веб-доменов могут конфликтовать с Custom Domain. Не включайте `workers_dev` для обхода ошибки настройки домена и не отключайте проверку CSRF. После публикации проверяйте `/api/health`, страницы и админку на `https://bao-cv.com`; список проверок приведён ниже.

Если когда-либо потребуется установка **в другом аккаунте**, работайте с отдельной конфигурацией, его собственными D1/KV и доменом. Не запускайте первоначальный импорт против уже заполненной рабочей базы. Для новой пустой цели сначала создайте её ресурсы, примените схему и импортируйте проверенный архив:

```powershell
npm run cf -- d1 migrations apply DB --remote --config ПУТЬ_К_ОТДЕЛЬНОЙ_КОНФИГУРАЦИИ
```

Инструмент `migrate-cloudflare.mjs` использует привязки текущего проекта: перед его применением в другом аккаунте настройте отдельную копию проекта и проверьте целевые ресурсы. Затем выполните команду импорта из раздела 3 с `--remote`. Это инструкция для новой установки, а не шаг очередного деплоя существующего сайта. [Автоматическое создание ресурсов Wrangler](https://developers.cloudflare.com/workers/wrangler/configuration/#automatic-provisioning).

Изображения в KV распространяются между узлами не мгновенно: новое или заменённое изображение может появиться в другом регионе через 60 секунд или позже. Не загружайте его повторно сразу после сохранения. Это [особенность согласованности KV](https://developers.cloudflare.com/kv/concepts/how-kv-works/).

Scopus необязателен: без ключа остаётся ссылка на профиль автора. Для интеграции используйте только **новый** ключ после отзыва ранее опубликованного:

```powershell
npm run cf -- secret put SCOPUS_API_KEY
```

Ключ вводится по запросу Wrangler. Не добавляйте его в `wrangler.jsonc` или клиентский код. Старые `MONGODB_URI`, `JWT_SECRET` и `SESSION_SECRET` не нужны Worker: MongoDB URI используется только локальным инструментом экспорта.

## 5. Подключение GitHub для следующих обновлений

Делайте это после первого успешного деплоя, создания таблиц и переноса данных. Сохраните выданные ID привязок в рабочей ветке; не публикуйте `.migration`, `.cloudflare`, `.wrangler` или секреты.

В Cloudflare откройте **Workers & Pages → bao-ws → Settings → Builds → Connect**, выберите свой GitHub-репозиторий и настройте:

| Настройка | Значение |
| --- | --- |
| Worker name | `bao-ws`, как в `wrangler.jsonc` |
| Production branch | `codex/react-security-upgrade` — ветка этой миграции |
| Root directory | Корень репозитория |
| Build command | `npm run build:cloudflare` |
| Deploy command | `npm run deploy:cloudflare` |
| Build variable | `NODE_VERSION=24.15.0` или совместимая более новая 24.x |

Установка npm-зависимостей выполняется системой сборки. Не включайте режим установки только production-зависимостей: Vite и Wrangler нужны на этапе сборки. После последующего переноса изменений в `main` явно переключите production branch в настройках.

Существующая интеграция Builds публикует только `bao-ws` через `npm run deploy:cloudflare`; её команду менять не требуется. `bao-cv-redirect` обновляется вручную командой `npm run deploy:cloudflare:redirect`, пока для него не подключена отдельная сборка. При необходимости подключите к нему тот же репозиторий и ветку с командой деплоя `npm run deploy:cloudflare:redirect` и конфигурацией `wrangler.redirect.jsonc`; отдельная сборка React для него не нужна.

Workers Builds проверяет, что публикуемый Worker соответствует Worker, к которому привязана сборка. Поэтому `npm run deploy:cloudflare:all` предназначена для локальной публикации обоих Workers: не подставляйте её в существующий Builds и не отключайте защитную проверку соответствия имени. [Требование совпадения имени Worker](https://developers.cloudflare.com/workers/ci-cd/builds/troubleshoot/#workers-name-requirement).

Первоначальный импорт данных не включается в каждый Git-деплой. Новые SQL-миграции применяются осознанно перед зависимым от них выпуском. Для тестовых веток не используйте production-привязки D1/KV: сама по себе отдельная версия кода не создаёт копию данных. [Подключение Git](https://developers.cloudflare.com/workers/ci-cd/builds/), [настройки сборки](https://developers.cloudflare.com/workers/ci-cd/builds/configuration/), [версия Node.js](https://developers.cloudflare.com/workers/ci-cd/builds/build-image/).

## 6. Домены bao-cv.com и www.bao-cv.com

До переноса DNS у домена использовались `ns1.ps.kz`, `ns2.ps.kz`, `ns3.ps.kz`. Назначенные Cloudflare серверы — `alexis.ns.cloudflare.com` и `cloe.ns.cloudflare.com`; на 9 ноября зона имеет статус Active. Повторно менять NS для публикации обновлений не требуется. Регистрация домена остаётся у PS Internet Company LLP (PS.kz).

В настройках зоны **SSL/TLS → Edge Certificates** включён **Always Use HTTPS**, минимальная версия TLS — **1.2**; TLS 1.3 также включён. Это настройки Cloudflare, они не применяются командами Wrangler из репозитория. Проверен действующий HTTPS-сертификат. При переносе в другую зону настройте перенаправление там, чтобы оно покрывало и статические файлы, которые обходят код Worker.

В Cloudflare сохраняйте существующие почтовые `MX`, `TXT`/SPF/DKIM/DMARC, записи подтверждения владения и поддомены. Хост `mail` должен оставаться DNS only с прежним IP. Настройка Custom Domain относится только к веб-именам `bao-cv.com` и `www.bao-cv.com`. Если потребуется повторный перенос DNS в другой аккаунт, используйте назначенные именно ему NS и официальный порядок переноса DNSSEC/DS: [Cloudflare](https://developers.cloudflare.com/dns/zone-setups/full-setup/setup/), [инструкция регистратора](https://docs.ps.kz/ru/domains/dns-management/change-ns-servers).

1. Сохраните прежние значения A/AAAA/CNAME веб-доменов для возврата. До завершения переключения оставьте старый хостинг и MongoDB доступными; не редактируйте две копии сайта параллельно.
2. В `wrangler.jsonc` основной Worker уже настроен на единственный Custom Domain `bao-cv.com`, а `PUBLIC_ORIGIN` — на `https://bao-cv.com`. В `wrangler.redirect.jsonc` отдельный Worker настроен на `www.bao-cv.com`. Имена в `routes` указываются без `/*`.
3. При конфликте существующего CNAME/A/AAAA заменяйте только записи соответствующего веб-имени в момент переключения. Не удаляйте почтовые записи. После устранения конфликта выполните `npm run build:cloudflare` и `npm run deploy:cloudflare:all`. Custom Domain создаёт необходимые DNS-записи и сертификат; дождитесь их готовности. [Настройка Custom Domain](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/).
4. Проверьте успешный HTTPS-ответ на `https://bao-cv.com/api/health`, `/index.html`, остальных `.html`, CSS и изображениях. Адреса `.html` должны сохраняться. Войдите в админку заново, создайте, отредактируйте и удалите проверочные сертификат и проект с изображениями, затем проверьте выход. Переключение origin не переносит прежнюю браузерную сессию.
5. Проверьте `https://www.bao-cv.com/certificates.html?check=domain`: ожидается **308** на `https://bao-cv.com/certificates.html?check=domain`. Сам `https://bao-cv.com` не должен перенаправляться обратно на `www` или технический адрес. Код перенаправления сохраняет метод запроса; авторизация выполняется только на основном origin.
6. Убедитесь, что технический адрес `bao-ws.bya20102005.workers.dev` и preview URL больше не обслуживают приложение. Это соответствует `workers_dev: false` и `preview_urls: false` в обеих конфигурациях. Зафиксируйте фактические результаты проверок после деплоя; этот документ их не подменяет.

Не привязывайте `www` непосредственно к основному Worker и не добавляйте второй origin для админки. Отдельный Worker перенаправления позволяет основному сайту сохранить бесплатную раздачу Static Assets без выполнения кода на каждый файл. Доменное перенаправление не добавляется в `_redirects`: [Workers Static Assets не поддерживает такие правила](https://developers.cloudflare.com/workers/static-assets/redirects/#advanced-redirects).

Выпуск сертификатов и обновление DNS могут занять время. Отключайте старое приложение только после проверки обоих доменов и сохранения резервных копий. Возврат старого хостинга сам по себе не переносит новые записи из D1 обратно в MongoDB.

## 7. Что обслуживать после переноса

Проверяйте Usage/Analytics для Workers, D1, KV и Durable Objects. Бесплатные квоты конечны; при их превышении операции могут перестать выполняться до сброса лимита. Не включайте платный тариф автоматически ради неразобранной ошибки.

Храните резервные копии и D1, и медиа KV: резервная копия одной базы не содержит изображения. Перед изменением схемы создавайте проверяемую копию данных. Обновления кода публикуйте через выбранную Git-ветку; контент добавляйте через защищённую админку — пересборка для обычного добавления сертификата не нужна.

Cloudflare-вариант проверяет тип, структуру и размеры JPEG/PNG/WebP и ограничивает размер 5 МБ и 20 мегапикселями. В нём нет Node-библиотеки Sharp: не следует считать такую проверку полной перекодировкой изображения или гарантированным удалением EXIF. Перед публикацией сканов убирайте ненужные персональные данные и метаданные файла.
