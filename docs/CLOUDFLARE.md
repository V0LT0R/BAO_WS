# Перенос BAO в собственный аккаунт Cloudflare

Этот вариант размещает сайт в аккаунте владельца: React-страницы и API работают в Cloudflare Workers, записи и учётные записи — в D1, изображения сертификатов и проектов — в Workers KV. SQLite Durable Objects обслуживают авторизацию и изменения контента. Дизайн, адреса `.html`, языки и возможности админки сохранены. Публикация через сторонний сервис Sites не используется.

На 8 ноября 2026 года приложение опубликовано как Worker `bao-ws`: https://bao-ws.bya20102005.workers.dev. В D1 перенесены 1 аккаунт и 37 записей; проверены вход, загрузка изображений сертификатов и проектов, редактирование, удаление и выход. Временные проверочные данные удалены. Привязки D1/KV закреплены в `wrangler.jsonc`. Домен `bao-cv.com` пока ожидает смены NS у регистратора; `PUBLIC_ORIGIN` временно соответствует техническому адресу.

## 1. Аккаунт и ограничения бесплатного варианта

Создайте свой аккаунт на [Cloudflare](https://dash.cloudflare.com/sign-up), подтвердите почту и включите двухфакторную аутентификацию. Используйте Workers Free и бесплатный план DNS-зоны. Для этого проекта не нужны R2, платный Workers или подключение платной подписки: не включайте их при настройке.

Это бессерверное приложение: отдельная виртуальная машина не запускается и не «засыпает». Процесс может заново инициализироваться при запросе; это не обещание нулевой задержки при любом обращении. Прогревать сайт регулярными запросами не требуется.

Основные квоты по документации на 8 ноября 2026 года:

| Ресурс | Бесплатная квота | Для чего используется |
| --- | --- | --- |
| Workers | 100 000 вызовов в день; 10 мс CPU на обычный вызов | API и маршрутизация |
| Static Assets | Запросы к статическим файлам бесплатны | React, CSS, шрифты, исходные изображения |
| D1 | 5 ГБ; 5 млн прочитанных и 100 000 записанных строк в день | Контент, пользователи, сессии |
| KV | 1 ГБ; 100 000 чтений и по 1 000 записей/удалений/списков в день | Загруженные изображения |
| SQLite Durable Objects | Доступны на Free; по умолчанию до 30 секунд CPU на вызов | bcrypt и последовательная обработка изменений |

Обычный Worker не выполняет bcrypt с коэффициентом 12: эта работа вынесена в `AuthService`. Квоты считаются на аккаунт; большой импорт тоже расходует лимиты KV. Перед переносом большого архива проверьте его объём и число файлов. Источники: [Workers](https://developers.cloudflare.com/workers/platform/limits/), [Static Assets](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/), [D1](https://developers.cloudflare.com/d1/platform/pricing/), [KV](https://developers.cloudflare.com/kv/platform/pricing/), [Durable Objects](https://developers.cloudflare.com/durable-objects/platform/limits/).

## 2. Подготовка и проверка на компьютере

Откройте терминал в корне проекта. Нужен Node.js 24.x, начиная с 24.15, и зависимости из lock-файла:

```powershell
npm ci
npm run build:cloudflare
npm run db:cloudflare:local
npm run test:client
npm run test:cloudflare
```

Сборка создаёт `dist`: десять React-страниц, собранные JS/CSS, разрешённые исходные изображения, шрифты, стили, поисковые файлы и `_headers`. Серверные исходники, `.env`, старые браузерные скрипты и карты исходников в статическую публикацию не попадают.

Для локального запуска:

```powershell
npm run dev:cloudflare
```

Откройте **http://localhost:8787**. Используйте именно этот адрес: он соответствует локальному `PUBLIC_ORIGIN`, который проверяется при входе и изменении данных. Локальные D1/KV хранятся в игнорируемой папке `.wrangler`; это отдельные данные, не облачная база.

Команды `npm run cf -- ...` запускают установленный в проекте Wrangler. Обёртка сохраняет локальные служебные файлы в игнорируемых каталогах и не загружает MongoDB-настройки из `.env` в Worker. MongoDB и Express для работы Cloudflare-варианта не нужны.

## 3. Перенос существующих записей и изображений

Сохраните резервную копию действующей MongoDB вместе с GridFS. На время окончательного экспорта остановите редактирование контента в старой админке, чтобы новые записи не остались только на старом сайте.

В экспорте указывается **точное имя исходной базы**, а не строка подключения. Вместо `NAME` подставьте имя из своей конфигурации. Если старая MongoDB URI не содержит имени базы, драйвер использует `test`; инструмент сверяет подтверждение с фактическим именем. Конфигурация читается из существующего локального `.env`:

```powershell
node scripts/migrate-cloudflare.mjs export --confirm-database NAME
```

Экспорт читает MongoDB и GridFS, не изменяя их; переносимые изображения локально проверяются и перекодируются в WebP. Скопируйте точный путь к созданному `manifest.json` из вывода команды. Архив в `.migration` содержит данные пользователей и хеши паролей: он исключён из Git, но его всё равно следует хранить как резервную копию с ограниченным доступом. Не отправляйте его в чат и не загружайте в репозиторий.

Сначала проверьте импорт локально; замените путь в примере своим:

```powershell
node scripts/migrate-cloudflare.mjs import --manifest ".migration/export-.../manifest.json" --local
```

Импорт рассчитан на **пустую целевую базу**, а для архива с изображениями — также на пустой namespace `MEDIA`. Если он сообщает о существующих данных или частично перенесённых файлах, не очищайте рабочее хранилище ради повторного запуска: сначала выясните, какой импорт уже выполнен. При переносе сохраняются существующие учётные записи и совместимые bcrypt-хеши; администратор входит своим паролем. Старые активные сессии не переносятся.

После импорта проверьте вход, списки проектов/опыта/активностей, изображения и оба языка. На локальной копии добавьте, отредактируйте и удалите пробный сертификат.

## 4. Первое развёртывание на workers.dev

Авторизуйте локальный Wrangler в своём аккаунте:

```powershell
npm run cf -- login
npm run cf -- whoami
npm run build:cloudflare
npm run deploy:cloudflare
```

В рабочем `wrangler.jsonc` уже сохранены выданные владельцу ID аккаунта, D1 `DB` и KV `MEDIA`. Последующие публикации используют эти же ресурсы. Повторно создавать базу, namespace или импортировать данные для обновления кода не нужно. Для установки в совершенно другом аккаунте сначала подготовьте отдельную конфигурацию с его ресурсами. [Автоматическое создание ресурсов Wrangler](https://developers.cloudflare.com/workers/wrangler/configuration/#automatic-provisioning).

Первый деплой создаёт приложение и хранилища, но ещё не переносит таблицы и данные. Примените схему, затем импортируйте тот же проверенный архив:

```powershell
npm run cf -- d1 migrations apply DB --remote
node scripts/migrate-cloudflare.mjs import --manifest ".migration/export-.../manifest.json" --remote
```

Возьмите **фактический** URL из успешного вывода деплоя, например адрес вида `https://bao-cv.ВАШ-ПОДДОМЕН.workers.dev`. Не используйте этот пример буквально. В `wrangler.jsonc` задайте `vars.PUBLIC_ORIGIN` равным своему адресу, без пути, затем выполните:

```powershell
npm run deploy:cloudflare
```

Теперь `/api/health` должен возвращать успешный ответ. Проверьте публичные страницы, вход администратора, создание/редактирование сертификата и проекта с изображением, выход и повторный вход. До создания таблиц или при неверном `PUBLIC_ORIGIN` ошибки API ожидаемы — это не повод отключать проверку CSRF.

Изображения в KV распространяются между узлами не мгновенно: новое или заменённое изображение может появиться в другом регионе через 60 секунд или позже. Не загружайте его повторно сразу после сохранения. Это [особенность согласованности KV](https://developers.cloudflare.com/kv/concepts/how-kv-works/).

Scopus необязателен: без ключа остаётся ссылка на профиль автора. Для интеграции используйте только **новый** ключ после отзыва ранее опубликованного:

```powershell
npm run cf -- secret put SCOPUS_API_KEY
```

Ключ вводится по запросу Wrangler. Не добавляйте его в `wrangler.jsonc` или клиентский код. Старые `MONGODB_URI`, `JWT_SECRET` и `SESSION_SECRET` не нужны Worker: MongoDB URI используется только локальным инструментом экспорта.

## 5. Подключение GitHub для следующих обновлений

Делайте это после первого успешного деплоя, создания таблиц и переноса данных. Сохраните выданные ID привязок в рабочей ветке; не публикуйте `.migration`, `.cloudflare`, `.wrangler` или секреты.

В Cloudflare откройте **Workers & Pages → bao-cv → Settings → Builds → Connect**, выберите свой GitHub-репозиторий и настройте:

| Настройка | Значение |
| --- | --- |
| Worker name | `bao-ws`, как в `wrangler.jsonc` |
| Production branch | `codex/react-security-upgrade` — ветка этой миграции |
| Root directory | Корень репозитория |
| Build command | `npm run build:cloudflare` |
| Deploy command | `npm run deploy:cloudflare` |
| Build variable | `NODE_VERSION=24.15.0` или совместимая более новая 24.x |

Установка npm-зависимостей выполняется системой сборки. Не включайте режим установки только production-зависимостей: Vite и Wrangler нужны на этапе сборки. После последующего переноса изменений в `main` явно переключите production branch в настройках.

Первоначальный импорт данных не включается в каждый Git-деплой. Новые SQL-миграции применяются осознанно перед зависимым от них выпуском. Для тестовых веток не используйте production-привязки D1/KV: сама по себе отдельная версия кода не создаёт копию данных. [Подключение Git](https://developers.cloudflare.com/workers/ci-cd/builds/), [настройки сборки](https://developers.cloudflare.com/workers/ci-cd/builds/configuration/), [версия Node.js](https://developers.cloudflare.com/workers/ci-cd/builds/build-image/).

## 6. Подключение bao-cv.com после проверки

На момент подготовки у домена использовались `ns1.ps.kz`, `ns2.ps.kz`, `ns3.ps.kz`. Перенос регистрации домена в Cloudflare не требуется; меняется управление DNS.

Регистратор подтверждён через RDAP: PS Internet Company LLP (PS.kz). В [консоли PS.kz](https://console.ps.kz/) откройте **Домены → bao-cv.com → Name-серверы (NS) → Персональные Name-серверы**. Назначенная этому домену пара: `alexis.ns.cloudflare.com` и `cloe.ns.cloudflare.com`; они должны заменить все три прежних NS. [Инструкция регистратора](https://docs.ps.kz/ru/domains/dns-management/change-ns-servers). В Cloudflare сверены существующие A/CNAME/MX/TXT; хост `mail` переведён в DNS only, его IP и почтовые записи сохранены.

1. Добавьте `bao-cv.com` в свой аккаунт Cloudflare и выберите Free. Сверьте импортированные DNS-записи с текущими: особенно `MX`, почтовые `TXT`/SPF/DKIM/DMARC, поддомены и записи подтверждения владения. Автоматический поиск не гарантирует полный перенос.
2. Пока домен должен вести на старый сайт, сохраните его прежние веб-записи. Старый хостинг и MongoDB продолжайте держать доступными.
3. Если у регистратора включён DNSSEC, выполните предусмотренный Cloudflare порядок переноса DS/DNSSEC до замены NS. Замените NS у регистратора **точно на назначенные вашему аккаунту Cloudflare**, дождитесь статуса Active; затем включите DNSSEC заново. Не придумывайте имена серверов. [Официальный порядок смены NS](https://developers.cloudflare.com/dns/zone-setups/full-setup/setup/).
4. После успешной проверки `workers.dev` задайте в `wrangler.jsonc` `PUBLIC_ORIGIN=https://bao-cv.com` и добавьте маршрут:

   ```json
   "routes": [
     { "pattern": "bao-cv.com", "custom_domain": true }
   ]
   ```

5. Выполните `npm run deploy:cloudflare`. При конфликте существующего CNAME сохраните старое значение и замените только запись веб-домена в момент переключения. Не удаляйте почтовые записи. Custom Domain создаёт необходимые DNS-записи и сертификат; для него используется имя хоста без `/*`. [Настройка Custom Domain](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/).
6. Проверьте HTTPS, `/index.html`, остальные `.html`, вход и сохранение в админке уже на `https://bao-cv.com`. Канонические ссылки сборки по умолчанию указывают на этот домен. Изменение адреса завершает прежнюю браузерную сессию — войдите снова.

Если нужен `www.bao-cv.com`, настройте в Cloudflare отдельное перенаправление **www → bao-cv.com** с сохранением пути и query string, включая проксируемую DNS-запись для www по инструкции Custom Domains. Не добавляйте второй самостоятельный origin для админки: проверка CSRF использует один `PUBLIC_ORIGIN`.

Смена NS и выпуск сертификатов могут занять время. Сначала дождитесь результата проверки, затем отключайте старое приложение. Сохраните прежние DNS-значения для возврата. Возврат старого хостинга сам по себе не переносит новые записи из D1 обратно в MongoDB, поэтому во время переключения не редактируйте две копии параллельно.

## 7. Что обслуживать после переноса

Проверяйте Usage/Analytics для Workers, D1, KV и Durable Objects. Бесплатные квоты конечны; при их превышении операции могут перестать выполняться до сброса лимита. Не включайте платный тариф автоматически ради неразобранной ошибки.

Храните резервные копии и D1, и медиа KV: резервная копия одной базы не содержит изображения. Перед изменением схемы создавайте проверяемую копию данных. Обновления кода публикуйте через выбранную Git-ветку; контент добавляйте через защищённую админку — пересборка для обычного добавления сертификата не нужна.

Cloudflare-вариант проверяет тип, структуру и размеры JPEG/PNG/WebP и ограничивает размер 5 МБ и 20 мегапикселями. В нём нет Node-библиотеки Sharp: не следует считать такую проверку полной перекодировкой изображения или гарантированным удалением EXIF. Перед публикацией сканов убирайте ненужные персональные данные и метаданные файла.
